## 02 Theme and Challenge

**Theme: Smart Urban Living**

> *"What digital solution can help urban communities better manage daily movement while improving first- and last-mile connectivity, pedestrian safety, and public-transport coordination?"*

Build a technology-based solution for a **real, identifiable problem** in an urban environment. Show how technology can improve how people **move, interact, and access services** in cities, with attention to practical implementation and community impact.

**Scope:** Your project may focus on **Makati City** or on similar urban challenges in other Philippine cities. Makati is a reference environment, not a requirement. Show how your solution could adapt to similar communities.

<details>
<summary><b>Possible focus areas (not limited to these)</b></summary>

<br>

- First- and last-mile transportation
- Pedestrian safety and accessibility
- Public transportation coordination
- Traffic and mobility management
- Commuter experience and information systems
- Smart navigation and route planning
- Urban accessibility and inclusivity
- Real-time mobility monitoring
- Data-driven urban planning
- Other technology-based solutions related to smart urban living

</details>

## 03 What to Build

> [!TIP]
> **Build a functional prototype, not a mockup, slide deck, concept, or proposal.**
> Prioritize **2-3 strong, working core features** over many unfinished ones.

The format must suit the problem. A prototype may be a:

| Software | Hardware |
|:---|:---|
| Web application | Hardware-enabled prototype |
| Mobile application (Android) | Software-and-hardware integrated system |
| Desktop application | |
| Navigation or commuter platform | |
| Data-driven system | |
| Interactive information portal | |

### A strong prototype demonstrates

- ✔ A clearly identified problem
- ✔ A practical solution
- ✔ Working core functionality
- ✔ A clear user or community benefit
- ✔ A meaningful use of technology
- ✔ Potential for further development or implementation

Aim for a "wow factor," but keep innovation realistic and demonstrable within 24 hours.

| ✔ Do | ✘ Don't |
|:---|:---|
| Ship 2-3 features that really work | Spread thin across many half-built ideas |
| Demo a live, running prototype | Rely only on slides or future promises |
| Show how it adapts to other cities | Hard-code it to one location |

## 04 Repository Rules

### Access and Ownership

- This repository was created by the organizers under the hackathon GitHub organization.
- **Your team may only edit your own repository.** Do not access, modify, or interfere with any other team's repository, accounts, or systems. Tampering with another team's work is grounds for **disqualification**.
- If you cannot push, or you can see something you believe you should not be able to access, **report it to the organizers immediately.** Do not try to work around it.
- Do not change repository settings, collaborator access, or visibility unless an organizer tells you to.
- Coaches and mentors have **read-only** access to this repository.

### Git Setup (before your first commit)

Set your name and email on every computer you will commit from:

```bash
git config --global user.name "Your Name"
git config --global user.email "your-github-email@example.com"
```

> [!IMPORTANT]
> Your commit email must be one of the emails on your GitHub account (**GitHub → Settings → Emails**). Otherwise your commits are not linked to you and **do not count as your contribution**.

### Starting from Scratch

The competition project **must begin at 1:00 PM on October 6, 2026.** The final prototype must reflect work done during the hackathon period.

| ✔ May be prepared | ✘ May NOT be prepared |
|:---|:---|
| Personal and GitHub accounts | Pre-written project code |
| Development environments, IDEs, code editors | A previously developed app presented as new |
| General-purpose templates | Existing repos used as the competition submission |
| Development tools and documentation references | Pre-built core functionality for this challenge |
| Open-source libraries and frameworks | Previously completed prototypes modified during the event |
| Technical knowledge and research | |
| Personal hardware components that are explicitly permitted | |

> [!CAUTION]
> **Do not commit or push anything before 1:00 PM on October 6.** You may accept the invite and clone this repository beforehand, but every commit dated before the official start is flagged automatically.

### Commit Regularly

Your commit history verifies that work happened during the hackathon, documents individual contributions, and supports troubleshooting.

- Commit and push **small and often**. Do not upload the whole project at the end.
- Use clear commit messages.

  | ✔ Good | ✘ Bad |
  |:---|:---|
  | `Add route search endpoint` | `update` |

- Commit under **your own GitHub account** so individual contributions are visible.
- Every team member should have meaningful, identifiable commits.
- Do not rewrite, squash, or delete history to hide or alter your development trail.

### Branches

- Branches are **welcome** and count toward your development trail.
- **Merge your work into `main` before the deadline.** What is on `main` at 1:00 PM on October 7 is your submission.
- Do not force push to `main`.

### What Goes in `.gitignore`

- ✔ Secrets and keys (`.env`, API keys), dependencies (`node_modules/`, `venv/`), build output, local data files
- ✘ **Never your source code.** Organizers check ignored files during verification.

## 05 Tools, APIs, AI and Hardware

### AI Tools: Allowed

AI coding assistants, chat tools, AI APIs, CLI tools, generative AI, and AI-assisted debugging and research are all permitted. AI is a **tool, not a substitute** for your team's technical work and decisions.

You remain responsible for:

- Understanding your implementation
- Testing generated code
- Correcting errors
- Integrating the solution
- Explaining how your system works
- Demonstrating the functionality of your project

### Open-Source First

Open-source frameworks, libraries, free tools, free datasets, publicly available resources, and free APIs are encouraged. Resourcefulness is part of the challenge, and no team should gain a big advantage from a paid service others can't access.

> [!WARNING]
> **Paid APIs and services must be disclosed.** Don't assume they're allowed. Organizers may allow, restrict, require a free alternative, provide an equivalent resource, or require you to demo without the paid dependency. The final list of permitted and restricted services will be announced before the hackathon.

## 08 Progress Checks

Organizers visit every team **every 1 hour** during the 24-hour period to monitor and document progress, confirm active work, spot technical problems, and verify compliance.

Be ready to show:

- Current working files
- GitHub repository and commit history
- Current prototype or working features
- Development progress
- Project documentation
- Individual member contributions

Failure to provide reasonable evidence of ongoing development may be reviewed by the organizing or technical committee.

### How Verification Works

Used for progress checks and milestone recognition:

1. **Only pushed code can be verified.** Commit and push before asking for a check.
2. Show `git status` (clean and up to date) and `git log -1`. Organizers match your commit to GitHub.
3. Organizers may run `git status --ignored` to confirm no source code is hidden in ignored files.
4. Organizers will **use your features themselves** on your machine, including inputs you did not prepare.
5. If your check happens after your claim, you may be asked to run the claimed commit (`git checkout <commit>`) for the demo.
